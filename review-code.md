# Staged v3 kit migration review

**Request changes before pushing.** The release build produces a kit that fails the pinned schema check. I also reproduced credential failures with the current Codex and Pi workloads.

## Findings

1. **High — The publisher changes the artifact after validation.** The check at `scripts/publish-kit.sh:140` passes, then the push at line 242 adds `org.opencontainers.image.revision` to every platform manifest. I exported the staged Codex kit with the release flags and ran the pinned `kit-tck validate` against that layout. It failed with **“org.opencontainers.image.revision must not be emitted”** (SPEC-v3 §9.3). The dry run exits before those flags are used, so a green rehearsal can precede publication of a nonconforming immutable tag. Validate the exact release artifact, including its metadata, before promoting its digest. [Publisher](scripts/publish-kit.sh) · [Kit specification](https://github.com/docker/sandbox-kit-spec/blob/v3.0.0-m.12/docs/spec/SPEC-v3.md#93-annotations)

2. **High — Consumers cannot recover the promised source revision from provenance.** The release build uses a directory exported from Git. I inspected its Buildx SLSA predicate and the checkout commit was absent. The commit appeared only in the OCI annotations. I served that layout from a local read-only registry fixture and ran the command documented at `docs/published-kits.md:68`. The pinned sbx v0.54.0 returned **“no provenance attached”**. It looks for a referrer on the kit digest, while Buildx puts attestations inside the image index. Signing the index does not create that referrer. Supply the revision through a supported provenance mechanism and make the release probe retrieve it by the documented command and compare it with the checkout SHA. [Release build](scripts/publish-kit.sh) · [Consumer instructions](docs/published-kits.md)

3. **High — A bound Codex GitHub credential leaves a fresh `gh` session logged out.** At `kits/sbxcodex/sbxcodex.yaml:91`, the only GitHub variable declared is `GITHUB_PERSONAL_ACCESS_TOKEN`. With just that variable set in Docker’s Codex workload, `gh api user --jq .login` exited asking for `gh auth login` or `GH_TOKEN`. It exits before sending an HTTP request, so the proxy has nothing to authenticate. This breaks the documented CLI workflow and the bound check at `tests/toolchain_test.sh:690`. **Design question:** Should the kit preserve authenticated `gh` in agent and `exec` sessions alongside GitHub MCP? I recommend preserving both and retaining their separate authenticated checks. [Codex descriptor](kits/sbxcodex/sbxcodex.yaml) · [Credential documentation](docs/agents.md)

4. **Medium — Pi’s unbound GitHub test requires a server that cannot start.** The kit always installs an MCP entry that expands `${GITHUB_TOKEN}`. With the staged config and no token, Pi 1.5.2 returned exit 1 from `pi mcp list --json` and reported that it could not resolve `GITHUB_TOKEN`. The test accepts the unbound credential at line 982, then requires that server to be connected at line 1001. Exporting an empty `GITHUB_PERSONAL_ACCESS_TOKEN` does not satisfy Pi’s lookup. **Design question:** Should an unbound Pi sandbox omit the GitHub server or expose anonymous GitHub tools? Make the config and the unbound assertion agree, while keeping the authenticated check for bound sandboxes. [Pi MCP config](kits/sbxpi/files/system/usr/local/share/sbxagent/pi/mcp.json) · [Toolchain test](tests/toolchain_test.sh)

5. **Medium — The host checks can exercise the wrong configuration.** The first create at `tests/lifecycle_test.sh:114` inherits `CROSS_SANDBOX_VISIBILITY`, then line 163 requires sibling traces to be readable. A supported private-mode export or repo `.env` makes a working mount fail this test. Set visibility explicitly for both creates. In the open-network instructions at `AGENTS.md:86`, the one-command `NETWORK_ALLOWLIST=false` assignment also expires before `make test-toolchain`. With no exported expectation, the test chooses its branch from the guest, so a dropped open-network mixin can pass as a correctly restricted sandbox. Pass the same explicit expectation to create and test. [Lifecycle test](tests/lifecycle_test.sh) · [Host instructions](AGENTS.md) · [Test target](Makefile)

## Verification and remaining gates

- `make lint`, all 29 wrapper unit tests under Linux `/bin/bash`, and `git diff --cached --check` passed. Native `linux/arm64` validation passed all 19 checks for each of the four kits and the open-network mixin. The release-flags build in finding 1 failed its separate check.
- The local builder supports arm64 only. The two-architecture kit build stopped at the first amd64 shell command with `exec format error`. The native build ran with `NETWORK_ALLOWLIST=false`, so it does not establish that a cold build works under the default allowlist.
- The credential probes used Docker workload index digests `sha256:23b3b8cc4646881208bacdc13d8238d7f3b883997c5e2bcff4f0b2fb3b452473` (Codex) and `sha256:fb40c183045a19a3faeca57822a3b8dea211131f3637e47fae1bc3170bbed2e9` (Pi). This environment has no signed-in host sbx session. Please confirm the plan’s disposable-host matrix after the corrections, including full and lite installs, both network modes, bound and unbound credentials, and trace persistence and visibility across restart.
- For the host pilot, exercise the first-launch MCP clients in an ordinary project as well as this checkout. The staged Claude test checks `gh` and config entries, and the Pi guard test checks the filter and extension registration. Those checks can pass even if the workload’s MCP gateway disappears or the loaded Pi extension fails to handle a blocked request. The throwaway registry publish, signing, revision lookup, and rerun remain release gates after branch CI.
